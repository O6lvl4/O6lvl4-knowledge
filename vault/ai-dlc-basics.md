AWS の開発方法論 AI-DLC を、はじめてチーム開発に入る人向けにかみ砕いたノート。目指すのは「明日から自分は何をするのか」がわかること。正確な定義・実装の詳細・批判まで含めた全体像は [[ai-dlc]] にある。元ネタは whitepaper の日本語訳(TextSmash の用語かみ砕きビュー経由)。

## 一言でいうと「AI が作業して、人間が OK を出す」

いままでは人間がコードを書き、AI が補助した。AI-DLC は逆だ。**AI が計画を書き、わからないことを人間に質問し、人間が承認してはじめて実装する**。

whitepaper 自身がカーナビに例えている。目的地を決めるのは人間。道順を出すのはナビ。「本当にこの道でいい?」を途中で見張るのも人間。運転(作業)の大部分はナビ側 = AI がやる。

## 覚える言葉は 3 + 2 だけ

| 言葉 | 意味 |
|---|---|
| **Intent** | 「何を作りたいか」の一文。すべての起点(例: クロスセル用のレコメンドエンジンを作る) |
| **Unit** | Intent を分割した、独立して作れるかたまり。Scrum のエピックにあたる |
| **Bolt** | 実際に作る短いサイクル。スプリントの代わりだが、2 週間ではなく**数時間〜数日** |
| **Mob Elaboration** | 全員で 1 部屋に集まり、AI の質問に答えながら要件を固める会(半日くらい) |
| **Mob Construction** | 全員で集まり、AI の提案(設計・コード・テスト)を見ながら作る会 |

Intent を Unit に割り、Unit を Bolt で作る。それだけ。分解案は AI が出してくるので、人間の仕事はそれが正しいか確かめることに絞られる。

## 開発は 2 フェーズで回る

1. **Inception(要件を固める)** — Mob Elaboration で AI が質問してくる(「主なユーザーは誰?」「達成したいビジネス成果は?」)。チームで答えると、ユーザーストーリー・Unit 分割・Bolt の計画ができあがる
2. **Construction(作る)** — Unit ごとに Bolt を回す。ドメイン設計 → 論理設計 → コード生成 → テスト、と進み、各ステップで AI が提案し人間が承認する

方法論の定義上は 3 つ目に Operations(運用)フェーズもあるのだが、v1 実装では中身が空のプレースホルダになっていて、**デプロイや監視はいままで通りの CI/CD と運用のやり方に接続する**設計になっている。Inception + Construction だけで回すのはこの設計通り([[ai-dlc]] の「2 フェーズ Bolt 運用」参照)。

## 自分がやることは「答える」「読む」「OK を出す」

- **質問に答える** — AI の質問はチャットではなくファイルに来る。選択式(A/B/C…)の下にある `[Answer]:` タグに書き込んで「Done」と返す
- **成果物を読む** — 計画・ストーリー・設計・コード。読んで違和感を口に出すのが仕事
- **承認する** — 各ステージの最後に「Continue(次へ)」か「Request Changes(直して)」を返す。AI は承認なしに先へ進めない仕組みになっている

一番大事なルールはこれ。**わからないコードに OK を出さない**。whitepaper は「デバッグできないなら所有できない」と言い切っていて、AI が書いた全行を開発者が理解することを譲れない条件にしている。1 年目でも「ここがわかりません」と言うのは立派な仕事のうち。実践報告でも、若手だけのチームが「なんとなく良さそう」で通してしまうのが一番の失敗パターンとされている。

## なぜこういうやり方なのか

AI は速い。ただし、間違った方向にも速い。だから各ステップに人間のチェック(**承認ゲート**)を置いて、間違いが雪だるまになる前に止める。whitepaper はこの人間の検証を「損失関数」と呼ぶ — 機械学習で誤差を測って早めに軌道修正する、あの損失関数の比喩だ。

もう一つの理由は待ち時間。開発が遅い本当の原因はコーディングよりも、調整会議・レビュー待ち・仕様の確認待ちにある、というのが whitepaper の診断。だから全員が同じ部屋に集まって AI と一緒に一気に決める(Mob 形式)。数週間かかっていた要件定義が半日で終わる、という理屈になっている。

## 気をつけること

- **ボトルネックは人間のレビュー速度になる**。AI の生成は速いので、自分が読むのが遅いと全体が遅くなる。ただし雑に読んで通すほうがずっと悪い
- **迷ったら破棄してやり直せる**。生成物の修正に固執しない。「違和感があれば修正せず破棄・作り直し可」は AWS 公式ワークショップのルールでもある
- **記録は全部残る**。生成物は `aidlc-docs/` フォルダに Markdown で残り、git で追える。あとから「なぜこう決めたか」を遡れる

## 押さえどころ（カード化候補）

- **AI-DLC を一言で** → AI が作業して人間が OK を出す開発方法論。AI が計画 → 質問 → 人間の承認 → 実装、の順で進む。
- **3 つの分解** → Intent(作りたいこと一文)→ Unit(独立して作れるかたまり)→ Bolt(数時間〜数日の実装サイクル)。
- **2 つの儀式** → Mob Elaboration(全員で要件固め)と Mob Construction(全員で構築)。どちらも 1 部屋に集まって AI と対話する。
- **自分の仕事 3 つ** → 質問に答える(`[Answer]:` タグ)・成果物を読む・承認する(Continue / Request Changes)。
- **一番大事なルール** → わからないコードに OK を出さない。「デバッグできないなら所有できない」。
- **運用フェーズは?** → 定義はあるが v1 実装は空。デプロイ・監視は既存の CI/CD に接続する。
